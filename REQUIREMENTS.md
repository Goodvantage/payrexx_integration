## 1. Purpose and Scope

`payrexx_integration` adds **Payrexx hosted checkout** as a payment gateway on
top of the upstream `frappe/payments` app (`required_apps = ["payments"]`),
following the same plug-in pattern as the gateways shipped inside `payments`
(Stripe, Paymob, …) but kept in its own repo so upstream `payments` is never
patched. It provides:

- the `Payrexx Settings` DocType (per-environment credentials) and automatic
  `Payment Gateway` registration,
- a thin Payrexx REST client for hosted Gateway creation and retrieval,
- HMAC-signed pay-by-email URLs for ERPNext Sales Invoices with a guest
  redirect endpoint that lazy-creates the checkout,
- the signed Payrexx webhook callback that settles confirmed payments, and a
  server-side success-redirect reconciliation fallback,
- an explicitly enabled, read-only hosted sandbox acceptance surface that
  verifies one site-configured invoice's provider-to-ledger settlement chain.

The app explicitly does **NOT**:

- modify upstream apps (`payments`, `frappe`, `erpnext`) — it plugs in via the
  `payments` registry pattern only;
- expose an app wrapper for the provider's documented Gateway DELETE, or
  implement capture, later-charge, void/cancel, or refund operations — those
  provider actions and their accounting reversals are manual procedures
  (REQ-PRX-BND-01);
- seed the ERPNext `Payment Gateway Account` bridge or any cross-app
  event/booking test data;
- depend on `good_connector` or any other Goodvantage app — downstream apps
  (e.g. `good_event`, `good_demo`) consume its API without a reverse
  dependency.

### 2.4 Payrexx REST Client

- REQ-PRX-API-01: Communicate with the Payrexx v1.x REST API using the current `x-api-key: <api_secret>` header auth (no legacy `ApiSignature` body field), a mandatory `?instance=` query param, provider-documented `application/x-www-form-urlencoded` POSTs, the `{status, data[]}` response envelope, and amounts in the smallest currency unit. Form encoding remains an official provider media type even though the official PHP SDK v2.0.15's bundled cURL/Guzzle adapters send JSON for non-file POSTs. [Trace: `payrexx/payrexx_client.py`, `payrexx_settings.py::_build_create_gateway_payload`, Payrexx `create-a-gateway` OpenAPI; Tests: `test_payrexx_client_uses_default_api_domain`, `test_gateway_payload_uses_per_checkout_failure_return_url`]
- REQ-PRX-API-02: Support Payrexx Platform / partner accounts through a host-only `api_base_domain` (instance = first subdomain of the login domain). Trust canonical `*.payrexx.com` API hosts by default; every custom final API host (for example `api.pay.goodvantage.ch`) must be listed exactly in the site-config JSON list `payrexx_allowed_api_hosts`. Reject userinfo, schemes, paths, queries, fragments, control characters, IP literals, malformed DNS names, wildcard entries, and every port except explicit HTTPS 443 before reading or sending the API secret. Retry the identical request once against trusted `api.payrexx.com` after 401/403 for every supported operation, and after 404 only for the credential probe or Gateway creation where 404 can identify an unprovisioned custom API host; therefore a custom-host Gateway creation can issue two POSTs, one to each host, on 401/403/404. Concrete retrievals and every other POST (including Subscription and QrCode creation) treat 404 as authoritative and never replay it to another host. This host fallback is distinct from rate-limit or transaction-deadlock retry. Neither the provider API nor this app defines an idempotency-key field, and Payrexx documents `referenceId` only as the merchant's internal reference, not as a uniqueness or de-duplication constraint. [Trace: `payrexx_client.py::_normalize_api_base_domain/_parse_bare_host/_configured_allowed_api_hosts/_should_retry_default_domain`, `payrexx_settings.py::PayrexxSettings._client`, Payrexx `create-a-gateway` OpenAPI; Tests: `TestPayrexxApiHostTrust`, `TestSubscriptionClient`]

Every final reversal raises a High-priority accounting-review ToDo on the exact source document, while `refund_pending` raises none. ### 2.6 Confirmation and Settlement

- REQ-PRX-SETL-01: Complete confirmed Integration Requests atomically: hydrate the row through one current locking read, store the provider transaction, validate the active payment chain, set Completed, settle the reference, and record the Payment Entry created by that settlement in one transaction, retrying the whole locked unit up to 3 attempts on `QueryDeadlockError`; duplicate confirmed callbacks, already-Completed rows, and terminal settlement-conflict rows must return without settling twice. [Trace: `payrexx_settings.py::_complete_integration_request/_complete_locked_integration_request`; Tests: `test_confirmation_retries_whole_locked_unit_after_deadlock`, `test_deadlock_retry_completes_request_and_creates_exactly_one_payment_entry`, `test_settlement_conflict_is_structured_terminal_and_idempotent`]
- REQ-PRX-SETL-02: A confirmed Payrexx Integration Request may settle when it references an existing inward Payment Request that remains submitted and `Requested` for an existing submitted Sales Invoice, or when an installed app's explicit `payrexx_settlement_source_providers` hook owns and revalidates a direct source under its own row lock. Standard settlement calls `set_as_paid()` under a Payment Request row lock; an accepted extension dispatches the source document's authorization hook only after canonical provider-evidence checks and extension validation. Sales Orders and every unowned source remain unsupported and become terminal settlement conflicts. [Trace: `payrexx_settings.py::_settlement_conflict/_extension_source_validation/_on_payment_authorized/_set_payment_request_as_paid`; Tests: core settlement tests and downstream Good NPO callback/reconciliation tests]
- REQ-PRX-SETL-03: Run every settings-controller checkout path, webhook/success settlement, subscription lifecycle/installment hook, scheduled subscription reconciliation hook, and accounting-review ToDo side effect as the owning `Payrexx Settings.automation_user` through a reentrant context manager that always restores the original session. Direct ERPNext/downstream `get_payment_url()` calls must execute source extensions, Integration Request writes, and provider setup inside that context; `pay_invoice` may nest it while creating the ERPNext Payment Request. ## 4. Explicit Decisions and Constraints

Documented intentional behaviors a reader might otherwise mistake for bugs:

- **Guest endpoints are intentional.** `pay_invoice`, `payment_success`, and `callback` are public by design (email links and Payrexx returns have no session). All newly issued links/returns and callbacks authenticate cryptographically. Only explicitly unmarked legacy Integration Requests retain unsigned `payment_success` compatibility, after which server-to-server confirmation remains mandatory. Documented in `SEMGREP_OVERRIDES.md`.
- **Chargebacks never touch the ledger.** A chargeback marks the Integration Request Failed and opens one review ToDo; submitted Payment Entries are deliberately preserved and reversal is a manual accounting procedure (`DOCUMENTATION.md` "Chargebacks", `HOW_TO.md` §9; audit finding H13).
- **No app Gateway-delete/capture/void/refund operations.** The provider documents Gateway DELETE, but the client surface is deliberately limited to `create_gateway`, `retrieve_gateway`, and `ping_gateway`; `refunded` webhooks leave the request status unchanged and provider-side actions stay manual (`DOCUMENTATION.md` "Supported Payment Operations").
- **Legacy gateway-unbound links.** Pre-gateway-binding tokens sign only the invoice name; they keep working with exactly one settings row and are intentionally rejected as ambiguous with several — resend the email to issue a gateway-bound link (`api.py::_verify`, `DOCUMENTATION.md` "URL Contracts").
- **Deterministic tokens.** Resending an invoice email with the same gateway reproduces the identical URL; rotating the site's `encryption_key` is the (rare) global invalidation mechanism (`AGENTS.md` "URL patterns").
- **Fail-closed checkout recovery.** An active Integration Request without a recoverable checkout URL raises an error instead of creating a second potentially chargeable checkout (audit finding H12; `api.py::_get_payment_request_checkout_url`).
- **Current-state checkout reuse.** A stored URL is not sufficient: current locking reads must prove the invoice remains wholly unpaid, the Payment Request remains submitted/Requested/fully outstanding, and all persisted checkout amount, currency, source, gateway, settings, and provider metadata still match. Partial or changed receivables stop before Payrexx contact (audit finding C3).
- **No core request-log commit.** Checkout creation intentionally does not call core `create_request_log()`, whose unconditional commit would persist an incomplete Payment Request/Integration Request before Payrexx succeeds. The app-owned insert and metadata save commit only with the caller transaction; rollback evidence supports manual cleanup of an unavoidable external orphan (audit finding H09).
- **Commit outcome has one framework-level ambiguity window.** Frappe clears `after_rollback` callbacks before issuing SQL `COMMIT`. A commit exception in that interval cannot trigger the rollback outcome callback, and the app cannot safely infer whether the provider Gateway or database transaction should be deleted. The immediate non-secret `local_commit_pending` journal entry closes the evidence gap; a successful commit adds `local_commit_confirmed`, an ordinary rollback adds `local_rollback_confirmed`, and an unpaired pending record remains a manual recovery finding. Internal commits and blind provider teardown are intentionally forbidden.
- **API host trust before secret access.** Canonical Payrexx-owned API hosts are trusted by suffix; custom platform API hosts require exact `payrexx_allowed_api_hosts` entries. URL-like/malformed/IP destinations are rejected before the Password field is read (audit finding H08).
- **Whole-unit deadlock retry.** Confirmation retries reload and re-settle the entire locked unit so a rollback cannot split Integration Request state from downstream settlement (2026-07-17 audit findings C3/H14; `payrexx_settings.py::_complete_integration_request`).
- **POST replay wording is host-specific.** Canonical POSTs have no rate-limit replay and checkout deadlocks are not retried after provider contact. Separately, a custom-host Gateway create currently sends the same POST once to canonical `api.payrexx.com` after 401/403/404. Neither an idempotency key nor documented `referenceId` uniqueness protects that second request; do not describe POST as absolutely "never replayed" (`payrexx_client.py::_post`).
- **Settlement conflicts are terminal.** The first conflict stores a versioned structured marker and evidence snapshot. Authenticated callback/success replays cannot clear it, even if later payload evidence would match. There is no automated reopen endpoint; current resolution is manual accounting review, refund/allocation as appropriate, and ToDo closure. A future automated resolution requires an explicit separately tested contract (`payrexx_settings.py::SETTLEMENT_CONFLICT_DATA_KEY`).
- **Sales Invoice sources only.** Payrexx rejects new Payment Requests sourced from Sales Orders or other doctypes before provider checkout creation. Existing unsupported checkouts cannot call `set_as_paid()` and instead become terminal settlement conflicts; no Sales Order advance is created because this app has no robust order-payable/idempotency contract.
- **Gateway status is not transaction evidence.** Success-return reconciliation ignores a Gateway-level `confirmed` status unless `invoices[].transactions[]` contains a confirmed transaction bound to the expected Integration Request reference. Already-Completed requests also require their stored confirmed transaction before the browser receives a success return.
- **Local automation-user helper.** `session_utils.as_automation_user` deliberately duplicates `good_connector`'s helper because this app must not depend on `good_connector`; there is exactly one implementation here (`session_utils.py` docstring).
- **Webhook `gateway_name` from the query string.** The callback intentionally reads request args/form dict in addition to kwargs because Payrexx posts JSON bodies (`payrexx_settings.py::_gateway_name_from_request`).
- **Not a Single, single-per-environment by convention.** `Payrexx Settings` supports multiple rows; environment separation is by naming convention (`Sandbox`/`Live`), and webhooks must carry `?gateway_name=` once more than one row exists (`AGENTS.md` "Gotchas").
- **Draft Payment Requests are never deleted by the pay-link flow (N11).** Ownership is not reliable provenance because a configured automation principal can also be used interactively. Only an exact submitted/Requested/fully outstanding row for the resolved gateway is reusable; any draft is preserved and blocks checkout creation until accounts staff resolve it. Failed current attempts roll back transactionally (`api.py::_get_or_create_payment_request`; `CUSTOM_APPS_AUDIT_2026-07-17.md` N11).
- **Only one active Payrexx request per invoice may create a Gateway.** Concurrent submission of separate full-value drafts is serialized on the Sales Invoice and followed by a current locking scan of all Payrexx gateways. One request may proceed; the other is preserved and rejected before provider contact. Paid, failed, cancelled, and docstatus-cancelled history is not treated as an active competitor.
- **Static QR targets are origin-bound, not just scheme-checked.** A static QR is permanent and printed, and upstream apps resolve their own public base (good_npo: `good_npo_public_base_url` → `good_demo_public_base_url` → `host_name`). A stale or mistyped value would otherwise mint permanent codes pointing at a foreign origin that neither layer notices, so `create_static_qr` accepts only origins the operator published here — exactly what `safe_return_url` accepts. An upstream app whose public base is not configured on the site fails closed before Payrexx is contacted (`payrexx_settings.py::_validate_webshop_url`; audit finding F8).
- **Only final provider failures are Error Log rows.** A QR deletion whose code is already gone is caller-tolerated, and intermediate rate-limit/custom-host fallback statuses are client-tolerated, so none creates an entry. One unrecovered transport/error-envelope/incomplete-response failure creates one context-free Error Log at the owning boundary; checkout and QR controllers never add an outer traceback log (`payrexx_client.py::_execute_request/_initial_expected_statuses`, `payrexx_settings.py`; audit finding F11c).
- **No cross-app test seeding.** The Playwright booking-email spec consumes an existing Good Event Booking via `TEST_BOOKING_NAME`; this app must not create Buzz/Event records (`AGENTS.md` "Architecture", `HOW_TO.md` §10).
- **Versioning.** App version tracks the Frappe major (`16.5.1` in `payrexx_integration/__init__.py`; `pyproject.toml` declares the package version dynamic and reads that source), per the bench custom-app versioning policy. `16.1.7` carried the C3/H08/H09 checkout-integrity fixes, competing-request serialization, aligned checkout/settlement locks, conservative commit-outcome evidence, and bounded boundary retries. `16.1.8` is the credential-disclosure patch release: the provider request path no longer exposes the API secret (or the payer payload) to framework traceback logging. `16.1.9` is the backward-compatible audit-fix release for app-owned automation users, authenticated new success returns with explicit legacy marking, operation-aware custom-host 404 fallback, and core Playwright CI coverage. `16.2.0` adds the static QR code surface (§2.12): `create_static_qr`/`delete_static_qr` and the TWINT `qrCodeSessionId`/`returnApp`/`appLink` checkout handoff for downstream donation QR flows, all running under the owning gateway's automation user. `16.2.1` accepts operator-configured alternate public return origins while enforcing exact normalized HTTP(S) scheme, hostname, and effective-port matching without downgrade or malformed-origin compatibility. `16.2.2` binds static QR targets to that same published-origin allowlist instead of a scheme check, and stops writing an Error Log row for a provider status the caller already tolerates. `16.2.3` is the provider-fidelity patch release found while auditing permissively licensed Payrexx SDKs: TEST-mode confirmations no longer settle real documents without an explicit per-gateway opt-in (§2.6), hex webhook signatures compare as decoded bytes, a non-JSON webhook body names the merchant setting that produced it, idempotent requests back off on the edge rate limit, and the API version is pinned in one place at `v1.16`. `16.3.0` adds provider-reversal visibility (§2.5): Payrexx-issued refunds, partial refunds, pending refunds, and disputes are recorded beside the settlement, raised to accounting as a ToDo, and commented onto the paid document through the new `payrexx_refund_notice_providers` extension point. Refund initiation and accounting reversal remain out of scope and manual. `16.4.0` adds the Subscription provider surface (§2.4, §2.5, §2.9): subscription CRUD, `subscriptionState` gateway signups, shape-isolated webhook routing, the signup-versus-installment split, the `payrexx_subscription_event_providers` extension point, and a daily reporting reconciliation sweep. This app still owns no recurring domain concept — it routes events to whoever owns the instruction. `16.5.0` is the coordinated cross-app consistency release: it makes the strict HTTP-origin parser and `safe_pay_url` public contracts for dependent apps, pins sanitized bounded Error Log behavior and retryable database propagation at that URL boundary, and bounds provider connect/read waits. `16.5.1` closes the remaining logging seam: final provider/pay-URL failures use one direct empty-metadata Error Log, intermediate retries and outer checkout/QR controllers do not duplicate it, and no live exception/frame is sent to Sentry.
